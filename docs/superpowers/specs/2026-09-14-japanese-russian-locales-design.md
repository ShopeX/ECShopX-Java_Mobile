# 日语、俄语语言包设计

## 目标

为 ECShopX VShop 增加完整的日语（`ja`）和俄语（`ru`）语言支持。现有英文资源包约有 4,153 个文案 key，两个新增语言包必须覆盖全部基准 key，不能依赖英文回退值。

## 范围

包含以下内容：

- 日语、俄语 locale JSON 的完整翻译。
- 本地存储语言码与 i18next 语言码的映射。
- 站点语言配置接口返回值到本地语言码的归一化。
- 语言选择器中的语言名称。
- H5 主包和微信小程序分包的语言资源加载及构建复制。
- 编译期文案表中的日语、俄语值。
- locale 资源校验与运行时接入验证。

不包含以下内容：

- 修改现有中文、英文、阿拉伯文翻译。
- 调整业务页面布局或业务逻辑。
- 新增语言切换页面之外的产品功能。

## 设计

### 资源基准与翻译规则

`src/subpages/i18n/locales/en.json` 是 key 集合和插值格式的唯一基准。`ja.json`、`ru.json` 必须满足：

1. key 集合与英文资源完全一致。
2. 每个 key 都有非空目标语言文案。
3. `${0}`、`${1}` 等插值占位符与英文文案数量和编号一致。
4. 日期、数量、百分比、金额、URL、品牌名和代码片段等非自然语言内容保持其语义和格式。
5. 重复出现的业务术语使用统一译法；按钮、提示、错误信息和页面标题优先采用自然、简洁的产品界面表达。

对于纯格式字符串或产品专有名词，目标语言值可以与英文相同；除此之外不允许通过复制英文值充当翻译。

### 运行时语言链路

语言码沿用现有存储侧格式：`zhcn`、`zhtw`、`en`、`ar`、`ja`、`ru`。新增映射如下：

- `ja` → i18next `ja`，接口别名包括 `ja-JP` 和 `jp`。
- `ru` → i18next `ru`，接口别名包括 `ru-RU`。

应用启动或站点语言配置生效时，先将接口返回语言归一化为本地存储码，再由 i18next 实例加载对应资源并切换语言。现有用户偏好、站点默认语言、缓存和失效回退逻辑保持不变。

### 资源打包

- H5 通过 `src/subpages/i18n/resources.js` 同步注册六种语言资源。
- 微信小程序继续将 locale JSON 转换为分包 JS，并通过 `subpages/i18n/resources` 异步加载。
- `ja`、`ru` 必须同时出现在资源注册、构建复制和资源加载判定中，避免开发环境可用而生产包缺资源。

### 编译期文案

`src/i18n/config-t.js` 继续只保留编译期需要的轻量内联文案，不引入完整 locale JSON。新增语言使用对应的日语、俄语值；运行期完整文案仍从 locale 资源读取。

## 校验与测试

实现后执行以下校验：

- JSON 解析和 key 集合校验：英文、日语、俄语资源结构一致。
- 翻译质量约束校验：检测非允许场景下与英文完全相同的值。
- 占位符校验：检测插值编号、数量和格式不一致。
- 语言码单元测试：覆盖 `ja`、`ru`、区域别名和接口语言码映射。
- 资源加载测试：验证 H5/小程序资源注册包含 `ja`、`ru`。
- 项目 lint 或相关构建验证，确认 Taro 编译不会因新增资源或映射报错。

验证失败时优先修正资源或映射，不改变既有语言的行为。

## 验收标准

- 用户可在语言选择列表中看到并选择“日本語”和“Русский”。
- 站点配置返回 `ja-JP`、`ru-RU` 时能正确切换语言。
- H5 和微信小程序均能加载日语、俄语资源。
- 日语、俄语各覆盖英文基准包的全部 key，没有英文占位回退。
- 所有插值文案在目标语言下仍能正确替换参数。
- 现有中文、繁体中文、英文和阿拉伯文行为不回归。
